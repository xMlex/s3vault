# Go — стандарты Golang

## Стиль и структура

- Следовать Effective Go и официальному Go Code Review Comments.
- Использовать gofmt и goimports.
- Предпочитать идиоматичный Go.
- Использовать стандартную библиотеку, если внешняя зависимость не даёт существенных преимуществ.
- Не создавать собственные абстракции вместо простых стандартных механизмов.
- Не использовать глобальные переменные для управления состоянием приложения.

## Архитектура

- Организовывать код вокруг бизнес-доменов и ответственности пакетов.
- Избегать чрезмерного дробления на пакеты.
- Не создавать пакеты с названиями common, utils, helpers без конкретной ответственности.
- Не экспортировать типы и функции без необходимости.
- Интерфейсы определять преимущественно на стороне потребителя.
- Не создавать интерфейсы с единственной реализацией без практической причины.
- Не использовать чрезмерно универсальные repository/service/factory абстракции.

## Ошибки

- Обрабатывать ошибки явно.
- Не игнорировать ошибки через `_` без обоснования.
- Использовать `%w` для сохранения цепочки ошибок при необходимости.
- Применять errors.Is и errors.As для проверки ошибок.
- Не использовать panic для обработки штатных ошибок приложения.
- Добавлять контекст к ошибкам на границах компонентов.
- Не дублировать логирование одной и той же ошибки на каждом уровне.

## Конкурентность

- Использовать goroutine только при реальной необходимости параллелизма.
- Определять владельца жизненного цикла каждой goroutine.
- Обеспечивать корректную остановку фоновых процессов.
- Использовать context.Context для отмены и ограничения времени операций.
- Не передавать context.Context через структуры.
- Исключать data races.
- Предпочитать простые механизмы синхронизации сложным самодельным решениям.
- Проверять конкурентный код с помощью go test -race.

## Тестирование

- Использовать стандартный testing.
- Тестировать публичное поведение и бизнес-логику.
- Предпочитать table-driven tests для однотипных сценариев.
- Использовать integration tests для проверки взаимодействия компонентов.
- Не создавать чрезмерно сложные mock-объекты.
- Не тестировать внутреннюю реализацию вместо поведения.
- Проверять граничные случаи и обработку ошибок.
