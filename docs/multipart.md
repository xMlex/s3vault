# Multipart в S3-фасаде шлюза

План реализации. Написан после того, как `archive` на реальном стенде упал на
объекте ~5+ МиБ с `405 MethodNotAllowed` от шлюза.

**Статус: реализовано.** Реализация — `internal/s3api/multipart.go`; разбор в
[architecture.md](../architecture.md#multipart-in-the-facade) и
[README.md](../README.md#multipart-через-фасад). Разделы ниже оставлены как есть: это
обоснование, а не описание кода, поэтому полезно знать, что было отвергнуто и почему.

> **Предусловие §4 не проверено.** Проверку «умеет ли multipart хранилище самого шлюза»
> нужно делать на стенде, против `s3.endpoint` шлюза, а не против `:8333`:
> `aws --endpoint-url <шлюз.s3.endpoint> s3api create-multipart-upload --bucket … --key .probe/t.bin`.
> Если хранилище multipart не поддерживает, §7 закрывает диапазон 5 МиБ … 5 ГиБ, а выше
> 5 ГиБ нужен §9.

---

## 1. Симптом

```
level=ERROR msg="process file" op=archive path=gitlab-cicd-analytics
  err="put novikov-tmp/gitlab-cicd-analytics: operation error S3:
       CreateMultipartUpload, https response error StatusCode: 405,
       api error MethodNotAllowed: The specified method is not allowed
       against this resource."
```

Клиент настраивает `s3.endpoint` на S3-фасад шлюза (`s3vault server`,
`internal/s3api`). Всё, что меньше ~5 МиБ, проходит; начиная с ~5 МиБ — нет.

## 2. Диагноз: 405 порождается нашим же кодом

Текст ошибки совпадает до байта с `internal/s3api/s3err/error.go:44`:

```go
MethodNotAllowed: "The specified method is not allowed against this resource.",
```

Его выдаёт `serveHTTP` (`internal/s3api/handler.go:125`), когда `classify` не
узнал запрос:

```go
op, reject, ok := classify(r.Method, bucket, key, r.URL.Query())
if !ok {
    a.metric("unknown", "method_not_allowed")
    s3err.WriteError(w, r, s3err.MethodNotAllowed, "")
    return
}
```

`classify` (`internal/s3api/handler.go:255`) обрабатывает только `GET`, `HEAD`,
`PUT`, `DELETE`; всё остальное, включая `POST`, падает в `default:` и даёт
`ok = false`.

Отсюда три следствия, которые важны для выбора места правки:

1. **Фасад не знает multipart вообще.** Ни `CreateMultipartUpload`, ни
   `UploadPart`, ни `CompleteMultipartUpload`, ни `AbortMultipartUpload`, ни
   `ListParts` в роутере нет — это не «сломано», этого кода просто нет.
2. **Отказ происходит до проверки SigV4 и до обращения к хранилищу.** Запрос не
   доходит ни до авторизации, ни до `ObjectStore`. Значит гипотеза «эндпоинт за
   прокси режет POST» отпадает: отвечает сам фасад.
3. **Хранилище тут ни при чём.** 405 не говорит ничего о том, умеет ли
   хранилище шлюза multipart. Это отдельный вопрос — см. §4.

## 3. Почему клиент уходит в multipart

`internal/adapter/s3/store.go:62` создаёт `manager.NewUploader(client)` с голыми
дефолтами AWS SDK (`feature/s3/manager@v1.22.44`):

| константа | значение |
| --- | --- |
| `DefaultUploadPartSize` = `MinUploadPartSize` | 5 МиБ (5242880) |
| `DefaultUploadConcurrency` | 5 |
| `MaxUploadParts` | 10000 |

Решение принимается в `upload()` (`upload.go:398`): uploader читает одну часть;
`err == io.EOF` → `singlePart` (один `PutObject`), иначе multipart. То есть
**граница — ровно одна часть**, и это не свойство s3vault, а поведение SDK.

Размер части с тех пор стал настраиваемым: `s3.multipart_part_size`
(`S3VAULT_S3_MULTIPART_PART_SIZE`, по умолчанию **5 МиБ** = 5242880) передаётся
в `manager.Uploader.PartSize`. Границы — С3-ские (от 5 МиБ до 5 ГиБ), проверяются
в `config.Normalize` (`0` = не задано → дефолт; любое другое значение вне диапазона — отказ с именем ключа). Это выбор писателя, а не согласование с хранилищем: клиент
шлёт столько, сколько задано, и AWS, MinIO и фасад принимают одинаково. Побочный,
но определяющий эффект: **размер части — это же порог начала multipart**. Дефолт
равен 5 МиБ, то есть тому, что SDK и так делал, — 12 МиБ режутся на три части.
Поднятие ключа двигает порог: при 25 МиБ те же 12 МиБ ушли бы одним
`PutObject`. `phase_facade_multipart` поэтому задаёт 5242880 явно (чтобы число
частей проверяло сборку шлюза, а не текущий дефолт) и отдельно проверяет сам
дефолт. Положительная сторона — меньше круговых походов; отрицательная —
память: SDK держит `Concurrency + 1` буферов ровно по размеру части, то есть
дефолт стоит примерно 30 МиБ в полёте, а каждый МиБ ключа добавляет ~5 МиБ.

Побочно: при отказе uploader сам зовёт `AbortMultipartUpload`
(`LeavePartsOnError = false`, `upload.go:873-884`), поэтому осиротевших частей
на хранилище не остаётся — отказ чистый.

## 4. Предусловие: хранилище шлюза тоже должно уметь multipart

Это главное предусловие всей работы, и без его проверки она может оказаться
бесполезной.

На `CompleteMultipartUpload` фасад собирает объект и заливает его в **своё**
хранилище одним вызовом `archive.UploadFile` → `Archive.upload` →
`s3store.Put` → `manager.Upload`. Для объекта крупнее 5 МиБ этот последний
снова уйдёт в multipart — уже **по хранилищу**.

> Если хранилище шлюза не поддерживает multipart, мы просто передвинем отказ на
> один хоп глубже, и файлы >5 ГиБ не заработают.

Проверка (против `s3.endpoint` самого шлюза, не против `:8333`):

```bash
aws --endpoint-url <шлюз.s3.endpoint> s3api create-multipart-upload \
    --bucket <бакет шлюза> --key .probe/t.bin
```

- вернулся `UploadId` → хранилище годное, работа по фасаду даёт полное решение;
- отказ → объекты >5 ГиБ в принципе не записать, и нужен другой путь
  (многообъектная нарезка; см. §9).

## 5. Почему не fallback в клиенте

Первым рассматривался обход на стороне клиента: одна попытка определить
поддержку multipart, при отказе — спулл тела в temp-файл и одиночный
`PutObject`. Отклонён по двум причинам.

**Нарушает инвариант «клиент не знает про шлюз».** Автоматическая деградация
означает, что поведение клиента зависит от возможностей пира. Формулировка из
AGENTS.md — «симметричное `mode` на обеих сторонах это инвариант конфигурации» —
здесь даёт то же самое: клиент не должен подстраиваться под то, что умеет
шлюз.

**Не решает их задачу.** Одиночный `PUT` ограничен 5 ГиБ — это ограничение
протокола, а не клиента (AWS: *«The largest object that can be uploaded in a
single PUT is 5 GB»*). У заказчика есть файлы больше 5 ГиБ, для которых
одиночный PUT невозможен в принципе. Обход починил бы только диапазон
5 МиБ … 5 ГиБ.

Побочно подтвердилось при чтении SDK: повтор той же попытки невозможен и без
probe — `nextReader()` читает первые 5 МиБ **до** `CreateMultipartUpload`, тело
пайпа не перемотать. И одиночному `PutObject` нужен `Content-Length`: в
`smithy-go/transport/http/request.go:59` несеекабельный reader без `Len()` даёт
`ok = false` → `Content-Length = -1` → chunked, что S3 не принимает.

## 6. Дизайн

Точка сборки частей — шлюз. Он уже умеет ровно то, что нужно: `handlePut`
(`internal/s3api/put.go`) спуллит тело запроса в temp-файл через `spoolReader`
и заливает его через `archive.UploadFile`, добавляя свой слой и считая хеш.
Multipart переиспользует тот же путь — с той разницей, что тело собирается из
нескольких файлов.

| Запрос | Ответ фасада |
| --- | --- |
| `POST /{bucket}/{key}?uploads` | создать сессию, вернуть `UploadId` |
| `PUT /{bucket}/{key}?partNumber=N&uploadId=X` | спуллить часть N, вернуть `ETag` |
| `POST /{bucket}/{key}?uploadId=X` | склеить части → `archive.UploadFile` → 200 с ETag объекта |
| `DELETE /{bucket}/{key}?uploadId=X` | удалить части и сессию → 204 |
| `GET /{bucket}/{key}?uploadId=X` | `ListParts` (для совместимости; наш SDK не зовёт) |

Клиент после этого не меняется **вообще**: ни ключей конфигурации, ни кода, ни
поведения. Он шлёт то, что уже шлёт, и перестаёт получать 405.

### Инвариант слоёв сохраняется

Собранный объект уходит в хранилище через обычный `Archive.upload`, поэтому
шлюз накладывает ровно **один** свой слой — как при обычном `PutObject`. На
egress `Fetch.Materialize` снимает этот один слой, и клиент получает свой
`S3VCTR01` обратно. Ни «слоёв больше», ни «клиент потерял свой слой» не
возникает: сборка частей происходит до наложения слоя, а не после.

### Проверка целостности

ETag части — MD5 от байтов части. `UploadPart` возвращает его клиенту; на
`CompleteMultipartUpload` фасад сверяет присланный список с записанным: номера
частей должны совпасть и идти по возрастанию (`InvalidPartOrder`), ETag —
сходиться, когда клиент его прислал (best effort, часть клиентов ETag не
шлёт). Полная сборка дополнительно считает SHA-256 проходящего потока — он идёт
в `ArchiveOptions.PlaintextSHA256`, и `Archive` повторно не хеширует файл.

## 7. Порядок реализации

### Шаг 1. Операции в порту

`internal/port/s3identity.go`: добавить `S3OpCreateMultipartUpload`,
`S3OpUploadPart`, `S3OpCompleteMultipartUpload`, `S3OpAbortMultipartUpload`,
`S3OpListParts`.

Расширить `opMetric` (`internal/s3api/handler.go:204`) новыми значениями, чтобы
они попадали в `s3vault_s3_requests_total`.

`internal/adapter/s3auth/static.go:35` править **не нужно**: `Allow` проверяет
только бакет и не различает операции. Это надо зафиксировать тестом, чтобы
новые опции не выглядели «забытыми авторизацией».

### Шаг 2. Роутинг — здесь исчезает 405

В `classify` (`internal/s3api/handler.go:255`) развести по query:

- `POST` без `uploads` и без `uploadId` → `reject = NotImplemented`
  (браузерная form-загрузка не поддерживается — это «узнано, но не сделано»,
  а не «метод неизвестен»);
- `POST` с `uploads` → `CreateMultipartUpload`;
- `POST` с `uploadId` → `CompleteMultipartUpload`;
- `PUT` с `partNumber` + `uploadId` → `UploadPart`, иначе `PutObject`;
- `GET` с `uploadId` → `ListParts`, иначе `GetObject`;
- `DELETE` с `uploadId` → `AbortMultipartUpload`, иначе `DeleteObject`.

Ключ обязателен для всех multipart-операций; без ключа — `InvalidBucketName`,
как сейчас.

Новые коды ошибок в `internal/s3api/s3err/error.go`: `NoSuchUpload`,
`InvalidPart`, `InvalidPartOrder`, `EntityTooSmall`, `MalformedXML`,
`InvalidRequest`. Без них клиент получит `InternalError` вместо actionable
текста.

### Шаг 3. Реестр сессий

Новый файл `internal/s3api/multipart.go`.

```go
type part struct {
    number int
    path   string // файл в спул-каталоге сессии
    size   int64
    etag   string // MD5 hex
}

type session struct {
    uploadID    string
    backendKey  string
    accessKeyID string
    createdAt   time.Time
    touchedAt   time.Time
    parts       map[int]part
    dir         string
}
```

- `uploadId` — 32 байта из `crypto/rand` в hex. Он же bearer-токен на
  спулленные данные, поэтому обязан быть непредсказуемым: знание id даёт право
  дописать чужую сессию.
- Сессия привязана к `AccessKeyID` и к `backendKey`. Каждый последующий запрос
  по `uploadId` сверяет оба; несовпадение → `AccessDenied`. Иначе любой
  аутентифицированный клиент дописал бы чужой объект.
- Мьютекс на реестр. Отдельный мьютекс на саму сессию не нужен: части пишутся в
  разные файлы, поэтому параллельные `UploadPart` (наш SDK шлёт 5 одновременно)
  не конфликтуют. Повторная загрузка той же части перезаписывает файл — так
  ведёт себя и S3.
- Реестр в памяти процесса. Сессии не переживают перезапуск шлюза; см. §8.

### Шаг 4. Обработчики

- **CreateMultipartUpload** — вычислить `backendKey` через существующий
  `a.backendKey(bucket, clientKey)`, создать каталог сессии в спул-каталоге,
  зарегистрировать, ответить XML `InitiateMultipartUploadResult` с
  `xmlns="http://s3.amazonaws.com/doc/2006-03-01/"`.
- **UploadPart** — `vr.Reader()` (как в `handlePut`) → `spoolReader` в файл под
  номером части, сохранить размер и MD5, ответить `ETag` в кавычках.
  Переиспользовать `spoolReader` не получится напрямую (он пишет в
  `os.CreateTemp`), нужен его вариант с заданным путём — вынести общий
  `spoolTo(ctx, dst io.Writer, r io.Reader)` и перевести на него `handlePut`,
  чтобы не было двух копий логики подсчёта хеша и `Sync`.
- **CompleteMultipartUpload** — разобрать XML тела, проверить номера и порядок,
  склеить части в один temp-файл (`io.Copy` по возрастанию `partNumber`, без
  загрузки в память), посчитать SHA-256 проходящего потока, вызвать
  `a.archive.UploadFile` с `ExplicitKey: a.clientPath(bucket, clientKey)` и
  `PlaintextSHA256`, затем `a.invalidateCache` — ровно как в `handlePut`.
  Ответ: `CompleteMultipartUploadResult` с ETag собранного объекта
  (`sha256(plaintext)` в кавычках, как у `handleGet`). Части и сессию удалить
  только после успешной загрузки, чтобы сбой не уничтожил данные.
- **AbortMultipartUpload** — удалить каталог сессии, снять с регистрации, 204.
- **ListParts** — XML `ListPartsResult` по записанным частям, по возрастанию.

### Шаг 5. Подчистка — часть работы, а не опция

Без неё прерванный multipart навсегда оставляет данные на диске, и ни один
таймер в s3vault этого не заметит.

- `sweepExpired` по образцу `cache.StartSweeper` (`internal/adapter/cache/disk.go:729`):
  пройти по сессиям, удалить те, у которых `touchedAt` старше TTL, снять с
  регистрации.
- Запускать на старте шлюза и раз в интервал. `touchedAt` обновляется на каждом
  `UploadPart`, поэтому активная длинная загрузка не вытесняется.
- Значения по умолчанию: TTL 24 ч, интервал 15 мин.

### Шаг 6. Лимиты

Из спецификации S3, плюс защита диска шлюза:

| Параметр | Значение | Источник |
| --- | --- | --- |
| максимум частей | 10000 | спецификация |
| минимальный размер части (кроме последней) | 5 МиБ | спецификация |
| максимальный размер части | 5 ГиБ | спецификация |
| максимум живых сессий | конфиг, по умолчанию 64 | защита диска |
| максимум байт на одну сессию | конфиг, по умолчанию 0 (без ограничения) | защита диска |

Превышение → `EntityTooSmall` / `InvalidRequest` с текстом, называющим конкретное
число, а не «ошибка лимита».

### Шаг 7. Конфигурация

- `server.multipart_dir` — каталог спулла частей. Отдельный ключ, а **не**
  переиспользование `cache.dir`: у кэша свои инварианты (TTL, sweeper,
  блокировки) и он по умолчанию выключен, а multipart обязан работать всегда.
  По умолчанию — каталог рядом с кешем или системный temp.
- `server.multipart_ttl`, `server.multipart_sweep_interval`,
  `server.multipart_max_sessions`, `server.multipart_max_bytes` (последний нужен
  таблицы лимитов §7; в исходном перечне шага он был пропущен).
- `s3.multipart_part_size` — размер одной части, которую пишет **клиент**
  (`S3VAULT_S3_MULTIPART_PART_SIZE`, дефолт 5 МиБ — то, что SDK делал и без
  ключа). В исходном плане ключа не
  было: считалось, что 5 МиБ от SDK достаточно. Добавлен после реализации, потому
  что дефолт в 5 МиБ — это 12 частей на файл в 60 МиБ, и размер части,
  оказывается, единственная ручка, которой клиент управляет числом запросов. Это
  по-прежнему не «клиент подстраивается под шлюза» (§5): значение не
  согласуется и не проверяется, а просто задаёт размер собственных запросов,
  одинаковый для AWS, MinIO и фасада.

Обязательный обвязкой по правилам репозитория: ключи в `envKeys`
(`internal/config/config.go:147`), пример в `s3vault.example.yaml` и
`.env.example`, чтобы прошёл `TestEnvKeysMatchConfigFields`.

### Шаг 8. Тесты

- **Юнит, `internal/s3api/multipart_test.go`** (существующий шов — `httptest` +
  `newTestAPIStore`, фасад уже покрыт так):
  - полный roundtrip через AWS SDK: `PutObject` файла ~12 МиБ → фасад отвечает
    без 405, объект в memStore собран из всех частей и совпадает с исходником;
  - `CompleteMultipartUpload` кладёт в хранилище **один** объект с одним
    gateway-слоем (проверка инварианта из §6);
  - out-of-order части (1, 3, 2) собираются правильно;
  - несовпадение ETag → `InvalidPart`;
  - `uploadId` чужого principal → `AccessDenied`;
  - неизвестный `uploadId` → `NoSuchUpload`;
  - `AbortMultipartUpload` удаляет файлы частей;
  - `POST` без multipart-параметров → `NotImplemented` (не `MethodNotAllowed`);
  - истёкшая сессия удаляется сборщиком, свежая — нет.
- **e2e, `scripts/e2e.sh`**: фаза `facade` сейчас проверяет `PutObject`;
  добавить загрузку файла >5 МиБ через фасад (MinIO multipart поддерживает, так
  что клиент пойдёт штатным путём) и проверку roundtrip. Это же будет первой
  живой проверкой, что probe-обхода больше не нужно.
- **verify**: новый скрипт не обязателен — существующие `verify-layers` и
  `verify-decrypt-detection` не затрагиваются, если инвариант слоёв сохранён
  (проверяется тестом из шага 8).

## 8. Известные ограничения реализации

- Сессия в памяти процесса: перезапуск шлюза теряет незавершённые multipart, а
  файлы частей остаются на диске до срабатывания сборщика при следующем старте.
- Сборка частей — последовательное копирование, поэтому на диске временно
  лежит примерно удвоенный объём объекта (части плюс склеенный файл). Для
  больших объектов нужен запас по месту; в кластере шлюзов с общим спул-каталогом
  не сойдётся — сессии привязаны к процессу.
- Лимит одного `CompleteMultipartUpload` — 5 ГиБ на нижнем уровне, только если
  хранилище шлюза не умеет multipart (см. §4). При умеющем хранилище объект
  уходит наверх штатным multipart и ограничение не действует.

## 9. Что делать, если хранилище шлюза не умеет multipart

Тогда §7 не даёт результата для файлов >5 ГиБ, и остаётся единственный путь,
который вообще существует без multipart: **многообъектная нарезка**.

- `key` → `key.part000`, `key.part001`, … плюс манифест с числом частей,
  размером и общим SHA-256.
- Затрагивает всё, что сегодня предполагает «один объект = один ключ»: `List`,
  `Delete`, `identity.ResolveRemote` и `Decide`, инвалидация кэша, фасад,
  `--delete-if-exists`.
- Это изменение модели объекта, а не обход, и оно заметно крупнее §7. Начинать
  его нужно только после того, как §4 доказал, что multipart недоступен —
  иначе это лишняя работа.

## 10. Порядок запуска в работу

1. Проверить §4. Без этого результат §7 может оказаться нулевым.
2. Шаги 1–2 (операции и роутинг) — уже снимают 405 для всех объектов <5 ГиБ,
   хотя и без сборки частей, поэтому за ними стоит отдельный smoke-прогон.
3. Шаги 3–4 — сборка частей.
4. Шаг 5 — сборщик, до первого же прогона в проде.
5. Шаги 6–7 — лимиты и конфигурация.
6. Шаги 8–9 — тесты и документация.

Шаги 2 и 5 — те, где пропуск даёт не «падающий тест», а тихую утечку диска в
проде. Их стоит делать в паре с соответствующей проверкой, а не после.

## 11. Что отклонилось от плана при реализации

Два расхождения, оба сознательные.

**Часть, загруженная, но не перечисленная в `CompleteMultipartUpload`, не ошибка.**
План формулировал проверку как «номера частей должны совпасть». Реализовано строже
мягче: каждый *перечисленный* номер должен существовать, числа должны идти по
возрастанию, а не перечисленные — отбрасываются, как это делает сам S3. Отвергать
такой запрос значило бы развернуть клиента, которого принимает настоящий S3, и
нечем было бы ему помочь, кроме повторной загрузки. Усечение, которое это допускает,
недостижимо через AWS SDK: uploader сверяет число частей со своим `expectParts` до
`Complete` (`manager/upload.go`). Проверено тестом.

**На сессии есть мьютекс, хотя план говорил, что он не нужен.** Не нужен для файлов:
части пишутся в разные файлы, и параллельные `UploadPart` (SDK шлёт пять сразу) не
конфликтуют. Но нужен для `parts` — это `map`, а конкурентная запись в map это
паника, а не race-репорт. Мьютекс на сессию, а не общий на реестр: `Complete` держит
сессию на всё время сборки и не должен блокировать `UploadPart` чужой загрузки.
