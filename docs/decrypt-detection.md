# Определение «зашифрован ли объект» при чтении

Статус: **закрыто.** `DecryptAuto` ветвится по полю `Enc` контейнера, а не по типу
локального шифровальщика, и при несовождении с `encryption.mode` читателя
возвращает ошибку вместо тихого копирования. Оба симметричных дефекта (H2 — `mode=none`
против чужого шифротекста, H5 — `enc=0` при `command`) исправлены одним заходом;
контракт закрыт тестами `internal/adapter/encrypt/detect_test.go` и
`internal/service/fetch_test.go`.

Все числа ниже переизмерены на текущем дереве против живого MinIO; стенды и их
вердикты приведены по фактическому выводу.

Модель развёртывания, заданная оператором и принятая за основу:

1. Все S3-клиенты подключаются **только** к `s3vault server` (к его S3-фасаду).
   К реальному S3 ходит **исключительно сервер**.
2. Клиент и сервер общаются **только по протоколу S3**.
3. Шифрование клиента — **его собственный слой**, за него отвечает клиент.
   Если у сервера дополнительно `mode: command` — это **второй, серверный** слой.

Воспроизведение (нужен живой MinIO на `127.0.0.1:9000`, бакет `s3vault`,
ключи `s3vault`/`s3vaulttest`):

| Скрипт | Что проверяет |
| --- | --- |
| `scripts/verify-decrypt-detection.sh` | детектор шифрования, T0–T7 |
| `scripts/verify-layer-ownership.sh` | матрица «сервер × клиент» через фасад |
| `scripts/verify-server-drift.sh` | дрейф конфигурации сервера |

Все объекты кладутся под уникальный префикс `verify-*/lay-*/drift-*`, отдельный
от стенда `make e2e`. Опорные числа: плайнтекст 15 байт, один слой 167 байт
(128 заголовка + 39 шифротекста), два слоя 295/319 байт.

Стенды запускаются по `make verify` (цели `verify-detect`, `verify-layers`,
`verify-drift`) и в CI отдельным шагом `e2e.yml`. Предусловия: MinIO на
`127.0.0.1:9000` и бакет `s3vault` — стенд проверяет их и отказывается работать
вместо того, чтобы «пройти» на пустом хранилище. Каждый стенд возвращает
ненулевой код при нарушении контракта.

## 1. Главный факт: контейнер добавляется на каждом проходе

Раньше я считал, что «клиентский слой» и «серверный слой» — это одно и то же
шифрование в разных местах. **Это неверно**, и проверяется размерами объекта.

Каждая сторона оборачивает данные в собственный контейнер `S3VCTR01`:

| Путь | Что происходит | Код |
| --- | --- | --- |
| Клиент, заливка | оборачивает файл в контейнер, шифрует по своему `mode` | `service.Archive` → `buildContainerHeader` (`archive.go:387`) |
| Фасад, приём `PutObject` | **тоже** оборачивает в контейнер и шифрует по своему `mode` | `internal/s3api/put.go:48` → `Archive.UploadFile` |
| Фасад, отдача | снимает **ровно один** слой | `internal/s3api/get.go:25` → `unwrapForDecrypt` |
| Клиент, скачивание | снимает **ровно один** слой | `internal/service/fetch.go:429` |

Измерено (`verify-layer-ownership.sh`): при симметричной конфигурации объект
в реальном S3 весит **два контейнера** — внешний серверный, вложенный клиентский.

| сервер | клиент | объект | внешний слой | чтение |
| --- | --- | --- | --- | --- |
| command | command | 319 б, 2 слоя | `Salted__` | плайнтекст, верно |
| command | none | 295 б, 2 слоя | `Salted__` | плайнтекст, верно |
| none | command | 295 б, 2 слоя | `S3VCTR01` | плайнтекст, верно |
| none | none | 271 б, 2 слоя | `S3VCTR01` | плайнтекст, верно |

**Все четыре клетки проходят.** Модель из трёх пунктов работает: симметрия
конфигурации даёт корректный обмен, каждая сторона снимает ровно свой слой.

### Следствие: в байтах нет «чей это слой»

Ни `S3VCTR01`, ни `enc=2`, ни магия `Salted__` не говорят, **кто** зашифровал.
Поле `enc` отвечает на вопрос «зашифровано ли», а не «кем». Маркера
владения слоем в формате нет.

Отсюда главный структурный риск: снимать слой нельзя безусловно, без сверки с
тем, чей это слой. Именно это и было исходным дефектом — `DecryptAuto` получал
только локальный шифровальщик, заголовок ему не передавался, и ветвиться по
`hdr.Enc` он не мог в принципе.

Контракт сейчас такой (`internal/adapter/encrypt/detect.go:17`): на вход идёт
`objEnc = container.EncName(hdr.Enc)` (`container/header.go:225`), и он —
источник истины. При расхождении с `Name()` читателя возвращается ошибка
`object requires encryption.mode=…`; `none` копирует, `native`/`command`
вызывают соответствующий decryptor.

## 2. Дрейф конфигурации сервера ловится детектором

Главный практический вопрос модели: оператор меняет `mode` на сервере, а
объекты уже лежат (`verify-server-drift.sh`).

| Сценарий | Результат | Чем поймано |
| --- | --- | --- |
| **A.** сервер `command → none` | **отказ, rc=1** | детектор: `Enc=command` против читателя `none` |
| **B.** сервер `none → command` | **отказ, rc=1** | детектор: `Enc=none` против читателя `command` |
| **C.** клиент `none` читает зашифрованный объект | **отказ, rc=1** | детектор: `object requires encryption.mode=command` |

Исторически A ловился побочным эффектом — фасад публикует
`x-amz-checksum-sha256` от `meta.SHA256` (`internal/s3api/get.go:56`), то есть хеш
логического плайнтекста, а не отдаваемых байтов, и AWS SDK отвергал ответ
(`checksum did not match`); B — падением cryptcp. Обе защиты сработают и дальше,
но **это больше не то, что их ловит**: сценарий A сейчас даёт `InternalError`
и **0 байт** тела, а не отвергнутый ответ с шифротекстом внутри, и ни один
криптопроцесс не запускается.

Прежний остаточный риск («клиент, не валидирующий checksum, в сценарии A
получит тихий мусор») **снят**: отказ происходит до записи хоть одного байта.

### Открытый пробел: причина не доходит до клиента

Фасад логирует точную причину на уровне `ERROR` (проверено на стенде):

```
level=ERROR msg="s3 materialize" op=s3.get \
  err="object requires encryption.mode=command, but reader is configured for none"
```

но в ответе клиенту отдаёт `s3err.WriteError(w, r, s3err.InternalError, "")`
(`internal/s3api/get.go:37`) — пустое сообщение, поэтому SDK печатает
`api error InternalError: We encountered an internal error` без указания
причины. Оператор без доступа к логам шлюза видит только «500». См. §7.

## 3. Containerless legacy — закрыто

**Статус: закрыто.** Механика ниже сохранена как история; в поддерживаемой
топологии зазор недостижим.

Объект **без** `S3VCTR01` с `Salted__`-пейлоадом при читателе `none` копируется
как есть: в `decryptLegacy` (`detect.go:38`) магия `S3VLT01\n` не подходит под
контейнер OpenSSL, поэтому `io.Copy` проходит без ошибки. Зафиксировано тестом
`TestDecryptAutoLegacy` («none reader copies command ciphertext verbatim (legacy
limit)»). `Fetch` пишет warning (`warnLegacy`, `fetch.go:450`).

**Почему это больше не открытый дефект.**

1. **Продюсер containerless-шифртекста убран.** Раньше единственным штатным
   источником был `layout=raw` (срезает контейнер при записи), и дрейф
   `command → none` давал ровно эту форму. Теперь `Config.Normalize`
   (`config/config.go`) отвергает `raw` вместе с `native`/`command`: в raw-сторе
   нет заголовка, а значит нет и `enc`-маркера, поэтому допускается только
   `encryption.mode=none`, и payload там всегда plaintext.
2. **Потребителя-нарушителя нет.** Каталоги/бакеты миров не пересекаются
   (подтверждено оператором): raw-стенды только `mode=none`, шифрующие стенды
   только `layout=container` (там всегда `S3VCTR01`, и работает
   header-driven-детектор). Значит containerless-шифртекст не появляется и не
   читается нигде.
3. **Настоящих до-конвертных объектов нет** в описанном развёртывании.

Тихий `io.Copy` остаётся в коде только как ветка обратной совместимости для
гипотетических до-конвертных объектов; это защитный контракт, а не открытая
проблема. Если его когда-нибудь захочется убрать окончательно — сделать
containerless-объект вне `raw` жёсткой ошибкой вместо копирования (см.
`problems.md` → «Закрыто»).

**Переоценка серьёзности.** При модели из трёх пунктов это не главная находка, а
ошибка конфигурации клиента: сам оператор объявил, что за шифрование клиента
отвечает клиент, и настроил его `mode=none` против `mode=command`. Опасность была
не в утечке шифротекста, а в том, что **отказа не было** — код выхода 0 и
испорченный файл. Теперь для raw-стора такой конфигурации не существует
(отказ на старте), а для S3/container закрыт детектор.

Наполнение кэша мусором на этом пути прекратилось: `verify-decrypt-detection.sh`
(T5) показывает пустой кэш, потому что отказ происходит до записи хоть одного
байта. Старые записи, созданные **до** фикса, живут до истечения TTL — кэш
намеренно не инвалидируется, оператору следует снести `cache.dir` (H3).

## 5. Находки по коду

### H1. Два канала (запись через шлюз, чтение мимо него) — **снято**

`download` строил хранилище через `newObjectStore`, который `remote.url` не
смотрел вовсе: клиент писал через HTTP-приёмник шлюза (2 слоя) и читал напрямую
из S3, минуя шлюз, то есть снимал только внешний слой. На диск попадал собственный
контейнер клиента, а не plaintext — при полностью корректной конфигурации.

Закрыто **удалением режима**, а не правкой: `remote.url`, HTTP-фронтенд
`PUT /files` и `server.token` убраны целиком, клиент и шлюз говорят только по
S3. Симметрия стала структурной, а не документированной. Ключи конфига
отвергаются на старте (`config.CheckRemovedKeys`, `config/config.go:236`), тесты
удалены вместе с кодом. Те же пункты (P2, P11) закрыты вместе с режимом в
прежней версии `problems.md`.

### H2. `mode=none` молча отдаёт шифротекст command-объекта — **исправлено**

`Passthrough` проверял только магию native-шифротекста `S3VLT01\n`
(`native.go:23`); command-режим отдаёт OpenSSL-контейнер `Salted__`, под эту
магию не подходит → `io.Copy` без ошибки. **39 байт мусора на диске при rc=0.**

Сейчас `hdr.Enc` доходит до `DecryptAuto` и сверяется с `mode` читателя:
`object requires encryption.mode=command`, rc=1. Измерено, T2.

### H3. Кэш не отравляет *между* режимами

Ключ кэша включает `encrypt.Fingerprint` (`internal/adapter/encrypt/fingerprint.go:13`),
а в него — `cfg.Mode`, поэтому режимы не видят записи друг друга. Моё прежнее
утверждение об отравлении кэша при смене конфигурации **было неверным** и отозвано.
Верно только узкое: записи, созданные мусорным кодом **до** фикса, живут до
истечения TTL.

### H4. Пропущенная проверка, а не замысел

На ту же логику есть guard на локальном бэкенде —
`internal/adapter/local/raw.go:17` (`peekContainer`): заголовок `S3VCTR01`
разбирается перед записью, raw срезает контейнер и хранит голый payload. На
S3-пути аналогичной проверки не было, при том что заголовок уже разобран в
`unwrapForDecrypt` и `h.Enc` доступен. **Исправлено:** `h.Enc` доходит до
`DecryptAuto` и сверяется с `mode` читателя.

### H5. Симметричный дефект: `enc=0` игнорируется — **исправлено**

`detect.go` снимал слой безусловно, поэтому объект с `enc=0` (открытый)
при `mode=command` всё равно уходил в decryptor и падал. Симметрично H2.
**Исправлено:** при `enc=0` читатель `command` отказывается
(`object requires encryption.mode=none`) до запуска decryptor'а. Измерено, T6.

### H6. У покрытия была дыра ровно в этой функции

`DecryptAuto` — 0.0% покрытия, все находки в функции без тестов. **Исправлено:**
контракт покрыт `detect_test.go` (матрица `enc` × читатель, containerless
legacy, реальный `*Command`) и `fetch_test.go` (download/materialize).
Текущее покрытие, T7:

```
detect.go:17  DecryptAuto     100.0%
detect.go:38  decryptLegacy    84.6%
detect.go:58  encryptorName    75.0%
```

Непокрытым остаётся `encryptorName`'s ветка `return "unknown"` — ветка,
недостижимая при текущем наборе `Encryptor`, поскольку все три реализации
(`Passthrough`, `Native`, `Command`) имеют `Name()`.

### H7. Мои прежние проверки врали о собственном предмете

Три инцидента, все — в моей проверке, не в коде:

- Первая «проверка roundtrip через сервер» на самом деле проверяла прямой
  доступ клиента к S3, потому что `download` не ходил на сервер. Падение
  вскрыло H1, а не «сервер не расшифровал». Я объявил причину по первому
  совпадению и починил тест под реальность, не поставив вопрос «а должно ли
  так быть».
- Матрица «сервер × клиент» мерила не то: объект создавался клиентом
  **напрямую в S3**, минуя фасад, то есть без серверного слоя. Все три
  «упавшие» клетки на самом деле мерили рассинхронизацию слоёв.
- `fakecryptcp` и клиентский детектор — в одном скрипте, общий KEK. Любая
  ошибка детектора маскировалась бы «успешной» расшифровкой, и наоборот.

Ошибочные версии проверок заменены воспроизводимыми стендами выше; в каждом
из трёх инцидентов дефект был в моей проверке, а не в коде.

## 6. Что должен сохранить любой фикс

1. **Формат байтов не меняется.** `S3VCTR01`/`S3VLT01` остаются, новая версия
   контейнера не вводится.
2. **Ровно один слой снимает каждая сторона.** Симметричная конфигурация
   обязана продолжать работать — это подтверждено матрицей из 4 клеток.
3. **Идентичность объекта не меняется.** Пропуск по-прежнему определяется
   `S3VCTR01` Range-заголовком; ETag хешем не считается.
4. **Legacy-объекты без контейнера** читаются как раньше.
5. **Отказ предпочтительнее молчания.** Восстановление `rc=0` + мусор
   недопустимо ни в одном режиме.

## 7. Открытые решения

1. **Причина отказа не доходит до клиента фасада.** §2: `handleGet` отдаёт
   пустой `InternalError`, тогда как `DecryptAuto` уже сформулировал точную
   причину. Оператор без логов шлюза диагностику не получает. Варианты: пробросить
   текст ошибки в `Message` ответа, отдать 412/403 вместо 500, либо документировать
   «смотри `s3 materialize` в логе шлюза». Не решено — это UX-решение оператора,
   не дефект безопасности: отказ уже громкий.
2. ~~Несимметрия слоёв.~~ Решено: явный отказ по `hdr.Enc` против `mode` читателя.
3. ~~Владение слоем.~~ Решено: маркер владения не вводится, формат не меняется;
   достаточно `Enc` + инварианта «одна сторона — один слой».
4. ~~Объём отказа при `mode=none` против чужого шифротекста.~~ Решено: только
   ошибка, без режима «выгрузить как есть».
5. ~~**Containerless `Salted__` под читателем `none`** (§3)~~ Решено: `raw`
   допускается только с `encryption.mode=none` (иначе отказ на старте), а
   пересечения миров нет — продюсера containerless-шифртекста не осталось.
   Тихий `io.Copy` остаётся лишь защитной веткой для гипотетических
   до-конвертных объектов.
6. ~~**Стенды не входят в CI.**~~ Решено: `make verify` прогоняет все три
   стенда, `e2e.yml` вызывает его отдельным шагом после `e2e.sh all`, логи
   стендов падают в артефакт `verify-logs`. Каждый стенд возвращает ненулевой
   код при нарушении контракта, поэтому шаг — настоящий гейт, а не отчёт.
   Проверено: с возвратом исторического поведения (`*Command` снимает слой
   безусловно) стенд детектора даёт 3 провала и ненулевой код, дрейф-стенд — 1.

## 8. Принятые решения

1. **H2/H5 исправлены (P1).** `DecryptAuto` получает `container.EncName(hdr.Enc)`
   из `unwrapForDecrypt` и сверяет его с `Name()` читателя: при расхождении —
   ошибка `object requires encryption.mode=…`; `none` копирует,
   `native`/`command` вызывают соответствующий decryptor. Тихие клетки закрыты,
   криптопроцесс при несовпадении не запускается, ни одного байта не пишется.
   Тесты: `internal/adapter/encrypt/detect_test.go`,
   `internal/service/fetch_test.go`.
2. **Формат не менялся.** Маркер владения слоем не вводится; `S3VCTR01`/`S3VLT01`
   те же (см. §6.1).
3. **Legacy без контейнера** — warning и прежняя детекция по магии/типу;
   `layout=raw` (тоже без контейнера) ограничен `encryption.mode=none`, поэтому
   его payload всегда plaintext и копируется корректно. Containerless
   `Salted__` под читателем `none` остаётся копированием только для настоящих
   до-конвертных объектов (осознанная плата за §6.4) — комбинация `raw` +
   `native`/`command`, дававшая эту форму штатно, теперь отвергается
   `Config.Normalize`. Кэш намеренно не инвалидируется: записи, созданные
   мусорным кодом до фикса, живут до истечения TTL, оператору следует очистить
   `cache.dir` (H3).
4. **H1/P2/P11 сняты удалением remote-режима.** Отдельного канала записи нет,
   чтение и запись идут одним `s3.endpoint`; расхождение «писали через шлюз,
   читали мимо» невозможно в принципе.
